# Python release research, 2026-10-25

The existing Python locks are not release-ready. They contain Starlette and
python-multipart versions inside recently published denial-of-service advisory
ranges. Initial inspection also identified application-construction and
commit-before-response defects, now repaired locally as recorded below. Candidate
versions are researched targets, not resolved, installed, or validated upgrades.

## Evidence boundary

Research window: **2026-02-25 through 2026-10-25**, inclusive. Sources are maintainer
release notes, tagged source, publisher package metadata, and maintainer security
advisories. A recent crawl date does not qualify an old publication. Tagged source
is used to establish the behavior shipped in a dated release, not to claim that
every line was first written in 2026. Advice derived from local code is identified
separately from fresh upstream changes.

Scope: `backends/fastapi`, `stacks/fastapi-react/backend`, and
`stacks/portfolio/backend`. The existing audit ledger was treated as leads and
checked against manifests, locks, Dockerfiles, dependencies, factories, auth
repositories/services, and portfolio repositories/models/services. No production
files or dependency locks were changed by this research.

## Implementation follow-up, 2026-10-25

The implementation task removed the unsupported `openapi_version` constructor
argument, changed `DBSession` to `Depends(get_db_session, scope="function")`, and
adopted native `async with` session ownership in all three backends. Current source
inspection confirms those changes. The task recorded both pre-fix failures in
`tests/release/test_python_lifecycle.py`: response-before-commit ordering and HTTP
201 despite a failed commit. Both cases now pass for each backend using the
existing standalone virtual environment. These checks cover the local lifecycle
repair; resolved locks remain unchanged, and candidate-version runtime and
PostgreSQL validation remain blocked. Findings below describe the initial
inspection unless explicitly marked as outstanding.

### JWT findings need narrower claims

The 2026-09-23 payload-recursion advisory covers PyJWT >=2.0.0a1,<=2.14.0 and
identifies 2.15.0 as patched. Its maintainer update limits confirmed impact to an
uncaught request exception, not a demonstrated process crash or authentication
bypass. The unauthenticated path requires `PyJWKClient` or disabled signature
verification. Application code uses a configured HMAC algorithm and verifies the
signature, so this pre-verification path was not found.
[GHSA-42vr-xj54-vc7v](https://github.com/jpadilla/pyjwt/security/advisories/GHSA-42vr-xj54-vc7v).

The 2026-09-11 header-recursion advisory's structured affected range is **2.13.0**,
patched in **2.14.0**. Its narrative also describes older implementations that only
catch `ValueError`. This is conflicting scope evidence, not a confirmed affected
range for locked 2.10.1. A bounded 5,341-byte malformed-header probe against the
installed 2.11.0 returned `DecodeError`, an `InvalidTokenError`, and did not
reproduce an uncaught error. Test the exact locked runtime and actual HTTP header
limits before assigning network impact.
[GHSA-8wjv-2p76-3863](https://github.com/jpadilla/pyjwt/security/advisories/GHSA-8wjv-2p76-3863).

The 2026-09-08 options-mutation advisory lists >=2.11.0,<=2.13.0 and still says no
patched version in its structured field. It requires reuse of a mutable options
mapping after turning signature verification off. The template creates a fresh
mapping and never does that. Locked 2.10.1 is outside the listed range. Do not turn
this advisory into an invented 2.15.1 remediation guarantee.
[GHSA-gvp8-978c-rx2q](https://github.com/jpadilla/pyjwt/security/advisories/GHSA-gvp8-978c-rx2q).

2.15.1 is the candidate because it follows the documented September security work
and corrects an encoding-compatibility regression in 2.15.0. Verify valid tokens,
expiry, required claims, invalid algorithms, malformed input, and refresh-family
invalidation. The reviewed code does not use JWK/JWKS verification or mixed
symmetric/asymmetric allowlists; those advisories do not establish a template
token-forgery flaw. [PyJWT changelog](https://pyjwt.readthedocs.io/en/stable/changelog.html).

## Required compatibility work

**Application startup, initial finding repaired locally:** all three factories
passed `openapi_version="3.1.0"` to `FastAPI(...)`. Version 0.145 removed unknown
constructor arguments. In 0.162.0,
`openapi_version` is explicitly an attribute and defaults to 3.1.0. Removing that
constructor argument was the required repair and is now complete.
`root_path="/api"` is deprecated since 0.146, so move the deployment prefix
to the ASGI server after checking direct and proxied route behavior.
[2026-10-18 release changes](https://fastapi.tiangolo.com/release-notes/#01450),
[0.162.0 application source, released 2026-10-23](https://raw.githubusercontent.com/fastapi/fastapi/0.162.0/fastapi/applications.py).

**Request contracts:** recent FastAPI releases changed empty file/form handling,
omitted defaults, JSON null handling, and parameter-model validation. Version
0.162 restores normal omitted-boolean/default semantics. Verify login forms,
optional profile edits, upload errors, pagination, and OpenAPI against actual
frontend requests. These changes require contract tests, not automatic rewrites
of every schema. [October 2026 FastAPI release notes](https://fastapi.tiangolo.com/release-notes/).

**Dependency surface:** the new `fastapi[standard]` metadata includes telemetry
SDK/exporter dependencies, CLI tooling, and `httpx2`. The service invokes Uvicorn
directly. Before retaining the extra, review whether these additions are useful
or whether explicit existing runtime needs are preferable. This is a dependency
tradeoff, not authorization to silently add an observability stack.
[0.162.0 dependency metadata](https://raw.githubusercontent.com/fastapi/fastapi/0.162.0/pyproject.toml).

**Database completion, initial finding repaired locally:** at initial inspection,
`DBSession` used `Depends(get_db_session)` without a scope and the manager committed after
`yield`. Recent tagged FastAPI routing executes the response before closing the
request exit stack. Ordinary mutations could therefore send success before a failed
commit. The function-scoped dependency and commit-failure regression now address
this ordering locally. Preserve deliberate replay-revocation commits before
raised auth errors when completing dependency upgrades.
[FastAPI 0.162.0 routing source](https://raw.githubusercontent.com/fastapi/fastapi/0.162.0/fastapi/routing.py).

**Cancellation and pool ownership:** SQLAlchemy 2.0.55 fixes cancellation during
session/connection context-manager exit and pool cleanup. At initial inspection,
the local manager manually called `await session.close()` in `finally`, while the
new native `AsyncSession.__aexit__` uses `_run_to_completion`. Native `async with`
session ownership is now implemented locally. The SQLAlchemy upgrade and tests
of cancellation, subsequent pool checkout, and orderly shutdown remain outstanding.
This is a concrete reason to take the 2.0.55 patch.
[2.0.55 release](https://github.com/sqlalchemy/sqlalchemy/releases/tag/rel_2_0_55),
[2.0.55 session implementation](https://raw.githubusercontent.com/sqlalchemy/sqlalchemy/rel_2_0_55/lib/sqlalchemy/ext/asyncio/session.py).

**Pool compatibility:** asyncpg 0.32 changes native-pool `min_size` behavior and
adds `init_size`. The template builds a SQLAlchemy engine, not an asyncpg native
pool, so do not rewrite SQLAlchemy pool settings based on that change alone. Check
connection teardown, PostgreSQL types, migration execution, and refresh races.
[asyncpg 0.32.0 release](https://github.com/MagicStack/asyncpg/releases/tag/v0.32.0).

## Runtime and deployment

The inspected Dockerfiles use `python:3.12-slim`, uv 0.13.5, and direct Uvicorn
startup. Production runs Alembic before `exec uvicorn`, with four workers,
`--limit-concurrency 200`, and `--limit-max-requests 10000`. These literals do not
prove the image's current Python patch or that four workers fit every deployment.

Python **3.12.15** is the verified 3.12 security release dated 2026-09-30. Python
**3.14.9** and **3.15.1** were released 2026-10-21. Keep the initial release matrix
on the current 3.12 deployment line with a verified patched base image, and test a
current 3.14 interpreter separately. Do not advertise 3.15 application support
solely because the manifest says `>=3.12` or some dependencies added classifiers.
The 3.12 release page contains stale feature-series boilerplate; the dated 3.15.1
release establishes that a newer series exists.
[Python 3.12.15](https://www.python.org/downloads/release/python-31215/),
[Python 3.14.9](https://www.python.org/downloads/release/python-3149/),
[Python 3.15.1](https://www.python.org/downloads/release/python-3151/).

uv 0.13.5 addresses compromised certificate-chain handling and updates managed
Python builds. Updating uv does not automatically replace an existing virtual
environment's interpreter. It also does not update the Python executable already
inside a separate `python:3.12-slim` base. Record the interpreter and base digest
actually tested. [uv 0.13.5 release](https://github.com/astral-sh/uv/releases/tag/0.13.5).

Uvicorn's March 2026 release work improves fragmented-body allocation; July work
changes startup-failure handling, worker replacement, and default WebSocket
implementation. Its latest HTTP/2 support remains experimental and opt-in. Retain
the existing HTTP/1.1 deployment initially and verify graceful shutdown, worker
recycling, failed migrations, startup errors, forwarded headers, and readiness.
The `uvicorn.workers` deprecation dates to 2024 and does not qualify as new
research. The already-written direct Uvicorn startup can be assessed using the
recent supervisor changes. [Uvicorn dated release notes](https://uvicorn.dev/release-notes/).

## Portfolio consistency findings

These are **local code findings**, not newly discovered upstream vulnerabilities.
No source within the required publication window was found that specifically
establishes a new media-transaction or singleton design requirement for this app.
Do not relabel an old general pattern as recent research.

- `MediaService.upload` writes the final file before database metadata commits.
  A failed database operation can leave an orphan. `delete_media` removes the file
  before the row deletion commits, so rollback can leave metadata pointing to a
  missing file. Database transactions do not cover those filesystem operations.
- `SingletonRepository.get_or_create` selects the first row and inserts if absent.
  Profile and SiteSettings have UUID primary keys and no singleton constraint.
  Concurrent first requests can both create different rows.
- Media reference columns such as `avatar_media_id` and `favicon_media_id` lack
  foreign keys in the inspected models. Deletion policy must define whether to
  reject referenced-media deletion or clear references.
- MIME allowlisting checks the client-declared type, not file bytes. Serving
  protections reduce browser consequences but do not establish file-format
  validity.

Engineering proposals, requiring implementation and PostgreSQL fault tests:
enforce a constant singleton key with database uniqueness plus a conflict-safe
creation path; define media-reference foreign-key behavior; and make upload/delete
recovery explicit. For modest local media, a database-backed pending/ready/deleted
state with retryable cleanup can make crash recovery observable. A simpler
commit-first deletion can leave recoverable orphan files on unlink failure.
Moving unlink after commit alone does not create atomic filesystem/database
transactions. Choose one documented invariant and test failures at each boundary.

## Verification needed before release

1. Review the candidate constraints, resolve all three environments with the
   pinned uv version and network access, then perform clean locked installs.
   Preserve manifest/lock parity across the shared auth core. Record actual
   interpreter/package versions; the existing host environment is insufficient.
2. Run package vulnerability checks on the resolved graph, including transitive
   packages. This report is a focused primary-source review, not a full SBOM audit
   or a claim that unlisted dependencies have no vulnerabilities.
3. Import each app, generate OpenAPI, and test real frontend login/token/profile
   and upload request shapes. Confirm direct backend and proxied `/api` behavior.
4. Run the PostgreSQL tests with independent transactions for concurrent refresh,
   replay revocation, logout, password changes, singleton initialization, and
   media commit failures. SQLite is not evidence for row-lock behavior or JSONB.
5. Run bounded malformed-form tests at both the ASGI boundary and through Docker's
   real proxy/server path. Confirm parser rejection and continued healthy service;
   do not infer a fixed parser from the service-level upload size check.
6. Build and start every Python-containing generated variant using its actual
   Compose recipes. Verify migrations, owner enrollment, persistent media,
   authenticated Redis, health, shutdown, and restart against clean disposable
   PostgreSQL resources.

Network dependency resolution and Docker/PostgreSQL execution remain blocked by
the execution environment reported by the parent task. Nothing in this report
claims those checks passed. The report identifies the next concrete work and its
acceptance boundaries; it does not certify the release.
