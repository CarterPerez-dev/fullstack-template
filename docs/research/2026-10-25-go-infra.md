# Go, infrastructure, and release research

Research date: 2026-10-25. Qualifying external evidence window:
2026-02-25 through 2026-10-25 inclusive. Dates below are maintainer release,
advisory, substantive update, or image-build dates, not crawler timestamps.

The Go variants need a supported toolchain and a coordinated dependency refresh
before release. The image tags and installer also need release verification.
This report records **candidate targets, not resolved or tested upgrades**.
No dependency lock, production file, deployment, or remote setting was changed
by this research task. Network resolution and Docker execution remain blocked
in the implementation session, so no container digest, full vulnerability scan,
or PostgreSQL runtime result is established here.

## Runtime inspected

Both `backends/go-backend` and `stacks/go-react/go-backend` currently declare
`go 1.25.0`; their `go.mod` and `go.sum` files matched byte-for-byte during this
review. The Docker builder is `golang:1.25-bookworm`, producing a static binary
for `gcr.io/distroless/static-debian12:nonroot`.

The HTTP process uses Chi and `net/http.ListenAndServe`. JWT verification uses
local ES256 keys through jwx/v3, explicit issuer/audience validation, and current
database user state. PostgreSQL access is sqlx through pgx's `database/sql`
adapter. Redis provides distributed rate limiting with a local fallback. The
optional OpenTelemetry exporter is an outbound OTLP/gRPC client. No gRPC server,
xDS server, SSH service, or remote JWK fetch is configured by this application.

Files read: both Go manifests and Docker/Compose files; `cmd/api/main.go`,
`commands.go`, and `commands_test.go`; `internal/server/server.go`; `internal/core/{database,migrations,
redis,security,telemetry}.go`; `internal/auth/jwt.go`; middleware and handler
call sites; Go-stack `frontend/nginx.conf`; root `install.sh`;
`template-tool/{release,cli}.py`; `.github/workflows/lint.yml`; and the existing
release-audit ledger. Implementation work is concurrent: the findings below
describe the inspected source and should be reconciled with its eventual diff.

## Code-derived architecture findings

These findings come from the local runtime source, not an external claim that
needs a publication date. They are separate from dependency CVEs.

Implementation follow-up, October 25: findings 1, 2, and 6 below are retained as
the baseline evidence. Both Go copies now enforce a 128 MiB in-flight Argon2
budget, validate stored hash parameters, cap JSON bodies at 1 MiB, reject trailing
JSON, and derive stable key IDs from SHA-256 public-key thumbprints. The complete
available race-test suites, vet, and formatting checks pass. Container load,
PostgreSQL, and external JWKS-consumer checks remain pending; locks are unchanged.

1. **Password work needs a memory budget.** `internal/core/security.go` allocates
   64 MiB for each Argon2id operation; the API container has a 256 MiB limit.
   Registration/login can run concurrently and the global token bucket permits
   bursts. Four overlapping hashes already account for the nominal memory cap
   before the rest of the process. Add bounded admission around password work,
   plus appropriate rejection behavior, and measure parallel auth in Docker.
   A successful package unit test is not evidence against container OOM.
2. **Bound HTTP bodies inside the Go service.** Auth and user handlers decode
   `r.Body` directly. The standalone backend exposes a host port; the frontend's
   NGINX 1 MiB limit cannot protect that route. Add an application body limit and
   verify oversized/chunked JSON, invalid trailing input, and normal requests.
   `ReadTimeout` limits time, not allocated body size. The HTTP server has its
   normal header defaults; this is not a claim of unlimited HTTP headers.
3. **Define the proxy trust boundary before changing rate-limit keys.**
   `KeyByIP` reads `RemoteAddr`, while NGINX sends `X-Forwarded-For`. Users behind
   NGINX therefore share its bucket. Trust only configured proxy peers, retain
   a direct-peer fallback, and test forged forwarding headers via both routes.
   The fresh Chi advisory above is directly relevant to the proposed repair.
4. **Redis outage is degraded coordination, not unconditional bypass.**
   `RateLimiter.allow` falls back to an in-process token bucket. The `FailOpen`
   setting only matters if that fallback itself returns an error. Each replica
   then enforces its own bucket and restart clears local state. Test that
   behavior; avoid documenting a plain Redis-down authentication bypass.
5. **Key-bootstrap recovery is implemented locally; container validation remains.**
   The initial review found public-first writes and existence-only validation.
   Current `commands.go` publishes complete, fsynced PEM files through
   no-overwrite hardlinks, persists the private key first, derives a missing
   public key, and validates the P-256 key pair. Damaged private keys, mismatched
   pairs, and public-only state fail explicitly without replacing signing
   identity. Source and test files match between both Go variants. The
   implementation task reports `go test -race ./cmd/api` passing in each copy:
   five tests cover recovery/repeat, mismatched pairs, damaged private keys,
   public-only state, and concurrent initialization. This research follow-up
   inspected those tests but did not rerun them. Read-only-volume behavior and
   initialization as distroless UID 65532 remain untested because Docker access
   is denied. Candidate versions and dependency locks are unchanged.
6. **Persist key identity as well as key material.** `NewJWTManager` chooses a
   random eight-character `kid` every process start although the private key is
   persisted. Derive a stable identifier from the public key or persist it with
   the key. Test restart/replica JWKS consumers. Current in-repo verification
   uses a local key directly; the finding is interoperability and rotation
   reliability, not established signature bypass.
7. **Keep migration constraints explicit.** The runner uses one transaction,
   an advisory lock, a migration prefix check, and SHA256 history checks. Those
   protect concurrent initialization and changed history. They also disallow
   operations such as `CREATE INDEX CONCURRENTLY` inside that transaction.
   Keep the limited model documented and test rollback, repeated invocation,
   concurrent runners, and modified-history refusal. An old database without
   the ledger needs a reviewed adoption procedure; silent stamping is unsafe.
8. **Separate database bootstrap privilege from ordinary API use.** Compose
   creates the database as `postgres`, and `.env.example` configures the API URL
   with that same role.
   A generated least-privilege app role would reduce the impact of application
   compromise. Separate migration privileges deliberately; prove first boot
   and upgrade permissions rather than changing only the username.

The bootstrap admin command already reads a bounded password from stdin and
refuses replacing an existing account through normal repository creation. No
public unauthenticated administrator-creation endpoint was found.

## Installer, release, and GitHub Actions

`release.py` refuses dirty public builds, embeds revision and per-variant
checksums into the zipapp, produces deterministic archive metadata, and writes
eight independent stack archives. The CLI verifies the selected archive's
embedded hash and rejects links, traversal, duplicate entries, private files,
and oversize downloads/extraction. `install.sh` resolves a release tag, fetches
over HTTPS, verifies a matching checksum, rejects dirty/wrong-version public
metadata, protects unrelated commands, and installs by atomic replacement.
These are useful controls already present in the inspected source.

The initial zipapp and `checksums.txt` come from the same release origin. That
detects corruption and later archive replacement relative to the installed
zipapp; it does not independently authenticate a compromised publisher or
bootstrap script. The website installer URL remains a separate hosting trust
boundary and its live bytes were not verified in this task.

GitHub's [Actions security roadmap, published 2026-03-26 and updated 2026-03-30](https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/)
explicitly discusses mutable action references, commit-SHA locking, and
privilege boundaries. It describes some features as future milestones; it is
not proof those proposed features are enabled in this repository. Current CI
uses `contents: read`, `persist-credentials: false`, ordinary `pull_request`,
and no release write token. Keep those properties. Actions are still pinned by
version tags, so resolve verified commit SHAs for the final workflow. Do not
assume a precise semantic-version tag is immutable.

For publication, assemble and verify every asset in a draft before making the
release immutable. The dated [GitHub CLI 2.101.0 release, 2026-09-15](https://github.com/cli/cli/releases/tag/v2.101.0)
provides a concrete current example of immutable assets and release
attestation. This repository's immutability setting, rulesets, and publication
permissions have not been inspected or changed. The existing workflow runs
checks and package construction; it does not publish a release.

An optional attestation-verification path can strengthen the installer without
making a GitHub CLI install an unconditional requirement. If `gh release
verify` or `verify-asset` is used, require a fixed current CLI. The maintainer
advisory [GHSA-8xvp-7hj6-mcj9, 2026-05-27](https://github.com/cli/cli/security/advisories/GHSA-8xvp-7hj6-mcj9)
documents authorization headers sent to TUF mirrors in versions through
2.92.0 and fixes this in 2.93.0. Nothing in the template currently calls those
commands; this is a constraint on the proposed verification step, not evidence
that any local credential was exposed.

The immutable-release GA announcement from 2025 and undated GitHub hardening
pages were excluded as fresh evidence. Recent dated releases, the 2026 roadmap,
and the CLI maintainer advisory provide the relevant current evidence instead.

   network access. Review the actual `go.mod`/`go.sum` diff, verify both copies
   remain equivalent, and run module checksum verification. Preserve existing
   dependency provenance; do not substitute handwritten checksums.
